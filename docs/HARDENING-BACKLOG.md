# Hardening backlog

Problems the October 2026 verification passes found and that are still open, with the reason each one was left. Everything critical or major from those passes is fixed; what remains here is minor unless marked. Add to this file instead of leaving a known problem only in a review thread, and delete an entry when its fix lands.

Updated 2026-10-07.

## Marketplace

- **A buyer's copy of a graph agent arrives needing configuration (major).** An install copies the graph, but any literal text in an API node's URL, headers or body, in a code node's source, or in the input of an `http_request` or `code_interpreter` tool node stays with the publisher, because nothing distinguishes a credential from harmless text. The buyer is told which nodes to fill in, not what the values were. A copy can arrive working once graphs can reference named secrets that each organization supplies for itself; that needs its own design, because a published graph must not be able to send a buyer's secrets to the publisher's server. Prompts, tools and source code are still copied as before.
- An owed contributor share is recorded and withheld from the publisher, but it is assigned to the contributor only when their payout profile exists, which happens when they open Revenue and Payouts. There is no background sweep.
- Shares that went to the publisher before contributor earnings were recorded are not recovered; nothing recorded them.
- A renewal that fails on every attempt is rotated to the back of the queue, not retired, and nothing alerts on it beyond the worker's error count.
- A subscriber who had not cancelled renewal keeps the 3-day grace period after a listing leaves monthly pricing, although no renewal can happen there.

## Offerings and jobs

- **A buyer can reject any deliverable inside the 72-hour window and is refunded in full after having read it (major, by design of the claim).** Each rejection is recorded as a dispute on the publisher and the reason is shown to them; nothing yet limits a buyer who rejects everything. A per-buyer rejection rate, and what to do above a threshold, is a policy decision.
- A paid job's use of the platform's free-model keys is metered on the job and taken from the publisher's share when the job settles. A job that is refunded (failed, expired, rejected) earned nothing, so its model usage is recorded but not charged to anyone. The free-tier limiter still counts it against the publisher's organization.
- In a paid job `http_request` runs only when the offering names it in `allowedTools`. Once a publisher names it nothing narrows it further: any method, any public address, and no check on what the request carries, so a buyer's input can still talk that agent into sending the offering's instructions out. The form and the docs say so. A per-offering list of allowed hosts would let a publisher use the tool without that exposure; it is not built.
- An agent that answers through its graph cannot be given `allowedTools`, so its `http_request` nodes never run in a paid job and there is no way to allow them. The dashboard's offering form sets `allowedTools` for agent offerings only; a workflow offering's can be set through the API, and a workflow step that is a graph agent then refuses the allowlist when the job runs, not when the offering is saved.
- `web_search` and `code_interpreter` are not treated as outbound. A search query goes to the configured search provider, not to an address the model chooses; the sandbox runner is required by its contract to have no network egress, which the API cannot verify.
- The offering's `termsVersion` is an unkeyed digest that covers the private instructions. It reveals nothing of them, but someone who already holds an exact copy of an offering's title, description, schema, checks and instructions could confirm the instructions against it. Keying it needs a server secret passed into the offering views.
- An API key may hire without `expected`. It is then hired at the offering's terms when the request arrives: the key's per-job cap bounds the price, and nothing bounds the delivery time or the checks. Requiring `expected` of keys too would break scripts that hire by id; the SDK sends it whenever it is given the offering.
- Only `expected` protects a buyer from an edit to an active offering. Requiring a pause before the price, delivery time, checks or instructions of an active offering can change would also stop a publisher from changing instructions under jobs that are funded and not yet started (a job's price, checks and output format are fixed at hire; the instructions are read when it runs).
- One JSON Schema validation is bounded (1,000,000 work units and 2,000,000 pattern-matching steps, together a few tenths of a second at worst, as measured on a development machine), and one compile is bounded by 500 subschemas, boolean schemas and dependency names included (about 0.15 seconds there). A request can still run several in a row on the event loop: up to 5 samples on `POST /api/offerings/validate` and on a save, and up to 10 `json_schema` or `regex` checks on one deliverable, each inside its own bound. Moving user-schema work to a worker thread, or yielding between checks, would take it off the request path altogether.
- The validation budget depends on ajv evaluating the work meter before any other keyword of a subschema, which ajv has no public option for: `services/jsonSchema.ts` reorders ajv's rule groups, refuses to validate if the meter is not first, and a unit test (a fan-out whose every evaluation fails) pins the behaviour. An ajv upgrade has to pass that test.
- ajv keeps every distinct `pattern` it has compiled for the life of the process (its code-generation scope is not emptied when a schema is evicted from the validator cache), so memory grows slowly with the number of different patterns publishers have ever saved.
- A schema whose root refers to itself with `"$ref": "#"` does not compile (ajv cannot resolve it with schema registration off, which is off so that one organization's `$id` cannot collide with another's). Recursion through `#/definitions/...` or `#/$defs/...` works.
- The confidentiality check catches only a verbatim run of eight words from the private instructions or a system prompt. A paraphrase, a translation or an encoding passes.
- A workflow job runs in the job runner's worker, not through the workflow queue, because that queue's worker (`queues/workflow-run.queue.ts`) binds steps as the owner's own batch run. When the job's time budget ends the run row records "worker shutting down" as its error, which is the wrong label for a deadline; the job itself is recorded correctly as expired.
- A worker that dies mid-job holds the job until its lease lapses (the run's budget plus a minute, so up to 16 minutes); the lease is not renewed or shortened by a heartbeat, so a short job waits out a long lease before another worker takes it over.
- A buyer's copy of a marketplace agent that no install row points at any more is not recognised as a copy (see the provenance item under Skills), so it could be offered. The sellability check refuses every copy an install row still names.
- A product run that throws fails the job at once and refunds the buyer; only a deliverable that fails its checks is retried. In the proof run (`docs/AGENT-JOBS-RUN.md`, sections E1 and I) a connection timeout to the model provider failed three paid jobs this way. A failure before the model was reached is safe to retry inside the job's time budget; one after a tool ran is not, which is why nothing is retried today. The chat core would have to say which kind it was.
- The dashboard's hire, accept, reject and cancel buttons are shown to every member; a member who is not an owner or admin is refused by the API (`insufficient_role`) and told why, after clicking. The web app has no notion of the signed-in member's role to hide them with.
- `apps/web/e2e/jobs.spec.ts` needs the seeded demo organizations (a buyer with credits, a publisher with an agent), a running job worker and a reachable model; it skips itself without `E2E_DEMO_PASSWORD`. It is not part of any CI run, and no accessibility scan (axe) is installed for it.
- The sweeper loads each kind of overdue job oldest first, up to 1,000 a tick. Rows that fail on every tick are retried every tick and are not rotated behind the others.
- Job input and output are stored on the job row with no retention policy, and a deliverable larger than 512 KB fails the job.

## Authentication and API keys

- A member removed from an organization keeps access on routes guarded only by `requireAuth` until their token expires (up to 24 hours). Role-gated routes and token refresh check the current membership. Closing the rest needs a per-user session version checked on every request.
- API-key scopes are enforced on `/v1` (`agents:invoke`, `workflows:invoke`), on offerings and jobs, and on installing a listing (`marketplace:install`). Spend scopes must be granted by name. On the rest of the API `requireRole` still lets every API key through, so a key cut down to one scope can still call the routes that have no scope of their own.
- A key granted `jobs:review` or `marketplace:install` has no spend cap; only `jobs:hire` carries caps. Accepting releases money already in escrow and an install charges at most the listing's price, so the exposure is bounded by what the organization already committed or by one listing price per call.
- Rolling an agent back to a version that has no graph snapshot leaves the current graph in place.

## Skills, tool loop and graph engine

- A buyer's copy of a marketplace agent that no install row points at any more still runs without the trial restrictions. Recognising it needs a provenance column on `Agent`, written when the copy is made.
- The knowledge search route still returns the embedding provider's error body (`services/knowledge.ts`, `trySemanticSearch`).
- After a hard kill, per-request `MarketplaceRevenue` rows left pending and graph executions left `running` are not reaped.
- On shutdown, in-flight graph runs get 15 seconds to settle (`GRAPH_RUN_DRAIN_MS`) and the queue workers stop after that; the Fly `kill_timeout` is 60 seconds, so the order and the budget should be reviewed together.
- An agent chat may run for 120 seconds (`AGENT_CHAT_TIMEOUT_MS`), longer than the shutdown drain. A chat cut off by a deploy is cancelled and refunded; one cut off by a hard kill leaves its marketplace charge pending (see the reaper item above).
- `/v1` uses the API's global CORS policy; there is no per-route browser origin policy for it.
- The agent file store's count limit is enforced under a 30-second lease. An upload that was already fully sent when the lease lapsed can land late and exceed the limit by one file. Nothing is deleted, so no data is lost.

## SDK and CLI

- The SDK's route table is maintained by hand. Checking it against the API needs a route inventory exported from `apps/api`.
- There is no `wheelsai stop` command; `agents.stopDeployment` exists in the SDK.
- **The landing page's CLI preview shows output the CLI does not print (major):** a latency figure, a tool count, a treasury address and a marketplace listing for a command without `--publish`. It is scheduled with the agent `/v1` endpoint and measured latency work, which make the endpoint and the latency real.
- The API accepts `enableWallet` and `walletConfig` on an agent deployment and ignores them (agent budgets, phase 3).
- `wheelsai logs` for an agent deployment has no logs to show until deployment log streaming is built.

## Workflows and the scheduler

- A workflow answered through `/v1` with `stream: true` opens the stream at once and delivers the finished answer as chunks. It is not token by token.
- The scheduler worker runs one tick at a time: the tasks of a tick run in a pool, but the next tick waits for the slowest of them, retries included.
- A scheduled workflow run that fails sends `workflow.failed`, not `scheduled_task.failed`.
- A model step in a workflow has not been run against a live GPU deployment; no Nosana deployment can be started locally. The same holds for streaming on a model deployment through `/v1`.

## Deploy and billing

- If a request that changed the replica count crashed after Nosana applied the change, the time until the status worker reconciles the count (about 5 minutes plus one tick) is billed at the old count.
- When Nosana had already stopped a deployment and no stop time was recorded, the final billing window ends at the last billed second, so up to one billing interval goes unbilled.
- A training job that completes normally does not have its leftover Nosana vault reclaimed. Cancelled and failed training jobs, and every agent deployment, are handed to the orphan sweep.

## Nosana access

Paying Nosana with a dashboard API key and prepaid credits, beside the wallet. Nothing here has created, started or stopped anything on Nosana. On 2026-10-07 our code was checked against Nosana's current API with read-only requests (the API document, the manager and node sources, GETs with the founder's key); what that settled is in `docs/NOSANA-DEPLOY-RUN.md`, "Settled by the 2026-10-07 verification", and the defects it found that would have failed or misbilled the first paid run were fixed in the same build (the paginated list and the exact name lookup, `running` and billing gated on an online endpoint, the Ollama definition, `required_vram`, jobs and events read from their own routes). The first paid run is the checklist in that document, and the items marked "the paid run settles this" are filled in from its results table.

From the verification, not done in that build:

- **The Nosana account and its key are shared with the founder's other project (major before launch).** Its spend lowers the same balance, and INSUFFICIENT_FUNDS halts every deployment on it, ours included. Any holder of an account key can read our confidential job definitions back in clear through `/deployments/{id}/revisions` and `/deployments/{id}/jobs/{job}`: `HF_TOKEN`, training callback secrets, signed dataset and adapter URLs. The key the verification ran with holds every scope, including `api-keys:manage` (it reads the plaintext of every key on the account), `wallet:sign` and `oauth-apps:manage`, and it was pasted into a chat. Two things to do, neither of them code: before the paid run, a narrower key (`credits:read`, `deployments:read`, `deployments:write`, `jobs:read`) with the all-scope key revoked (keys have no expiry, so only revoking ends it); before launch, a Nosana account that only WheelsAI uses. Nothing in our code checks the key's scopes; a missing one shows as a 403 `INSUFFICIENT_SCOPE` on the first call that needs it, and should read as a configuration error, not an outage.
- `toNosanaJob` builds a node URL from the node's public key (`https://<node>.node.nos.ci`, `services/nosana.ts`), and OpenClaw uses it (`services/openclaw.ts`). That host is the node's management API, which needs signed requests, and `.node.nos.ci` is not the current domain (`.node.k8s.prd.nos.ci` is). The URL to use is the deployment's endpoint URL whose `online` is true. Only the one-shot job path builds it, which API-key access already refuses, so the paid runs do not touch it.
- vLLM runs from `vllm/vllm-openai:v0.6.0` / `v0.6.3`, which no market pre-pulls, so every vLLM start pulls several GB on the node before it can serve. The markets cache `docker.io/vllm/vllm-openai:v0.10.2` (and v0.9.2 on most). Moving the tag needs the tool-call parsers, the LoRA flags (`--enable-lora`, `--lora-modules`, the `--max-lora-rank` steps) and the adapter bootstrap re-tested on the new version first; they are pinned to 0.6.x behaviour. Until then the first paid serving run records the pull time.
- The API-key backend is still `https://dashboard.k8s.prd.nos.ci` with the `/api` prefix, through `@nosana/sdk` 0.4.74 (pinned exactly: 0.4.87 drops the prefix, reads only the first page of the list and fixes nothing we need). Nosana's documentation now names only `https://api.nosana.com`; the two are the same proxy today (same addresses, byte-identical GET responses), which is not a promise. After the paid run: move the base URL to `https://api.nosana.com`, then replace the API-key port with our own small REST client, typed from the published OpenAPI document or `@nosana/types` (about eight more endpoints; the list, jobs, events, credits and markets are already our own fetches). That gives real status codes and error bodies, and removes the SDK's `owner` parse and its error formatter, which drops a 400's reason and can throw a `TypeError`. `@nosana/kit` 2.16.0 is the documented client and was not chosen: it is ESM only on `@solana/kit` 8 types, sets no timeouts or retries either, and its JSDoc is wrong on the timeout unit and the balance unit. The wallet path stays on the SDK until it is retired. An advisory read of `GET /nodes/queued-nodes?marketAddress=` (idle nodes per market) in the operator view and the access check would go in with it.

Known before the verification:

- **The timeout unit is minutes (settled 2026-10-07, not yet confirmed on a deployment of ours).** Our settings are in seconds and are converted only where they are sent to Nosana, by `NOSANA_TIMEOUT_UNIT`, default `minutes`. The API document, the manager source and the relisting clock of live deployments on the account all say minutes; step 5 of the paid run confirms it with a $0.008 debit. In minutes the SDK refuses an update below 60, so no timeout under one hour can be set after create (`nosana_timeout_too_short`), and a decrease does not shorten a running job.
- OpenClaw still starts a one-shot Nosana job (`submitJob`), which only a wallet can list. With API-key access there is no private equivalent (the credit-paid job API pins the definition to public IPFS), so starting or restarting an OpenClaw deployment answers `501` with reason `nosana_one_shot_unavailable`. It moves to a Deployment-Manager deployment when its image is built. Its stop is wrong in wallet mode too: it passes the on-chain job address to `stopDeployment`, which expects a Deployment-Manager id, logs the failure and marks the row stopped regardless. `routes/launch.ts` (not registered) and `demo/gpu-metering-demo.ts` call `submitJob` as well and get the same refusal.
- The treasury settlement and payment-submit queues (an agent treasury paying its compute bill in SOL) were left as they are. They read job status with `getJobStatus`, an on-chain read, using the ids in `nosanaJobIds`, which hold Deployment-Manager ids; the read then returns a "running" stub whose start time is now, so the compute seconds are 0. `payment-submit` pays the host node's public key directly, which is not how Nosana is paid in either access mode (the vault, or the platform's credits, already pay the host). Neither queue knows about access modes.
- A row whose Nosana id was created by an access mode this process has no credential for (the wallet key removed after a switch to an API key, or the reverse) can be neither read nor stopped from here. Scale answers `409` (`nosana_access_mode_unavailable`) and restart `409` (`previous_run_other_account`); the workers log such rows once per tick. The owner is not charged for it: the billing worker moves the row's cursor forward without a charge, so the platform carries that GPU time, and it is not billed later in one piece either. An owner's stop is accepted: the row is marked stopped and its hold released with no final charge, while the deployment on Nosana is NOT stopped; the row keeps its id and mode (an agent row hands them to an orphan record), the reclaim sweep stops it once the credential is back, and the operator view lists it under `unreachable` until then. Still open: nothing alerts on such rows, nobody stops them on Nosana while the credential is away, and a row nobody stops stays `running` in our records even after Nosana halts it. Nothing refuses to boot over it.
- Training jobs store the access mode with their Nosana id, cancel through it, and hand it to the orphan record on a cancel or a failed submit (`services/trainingNosana.ts`). What is still missing for training: the route does not run the deploy pre-flight before it creates the row, and a cancel whose mode has no credential here marks the job cancelled and leaves an orphan record the sweep cannot act on until the credential returns (listed under `unreachable`).
- With both credentials loaded and `NOSANA_NETWORK` unset, each keeps its own network: the wallet the one derived from `SOLANA_NETWORK`, the API key mainnet. Market costs are read per backend. `NOSANA_API_URL`, when set, is used for the market list of both, which is right for the loopback stand-in and wrong for a real custom backend beside a wallet on another network. The wallet client's own backend is always the SDK preset for its network.
- With API-key access a deployment or a scale-up is refused (`503`, reason `gpu_cost_unavailable`) when Nosana's market list gives no cost for the tier's market and none was seen in the last 24 hours. The last-seen cost lives in process memory, so a restart during an outage of the market list pauses every new deployment until the list reads again. The public status component and the operator view's minimum still estimate an unpriced tier at retail, so `/status` can read "operational" while a tier, or during such an outage every tier, is refused.
- With the default unit of seconds, if Nosana reads minutes, the credit gate under-estimates what Nosana reserves by sixty times. The boot warning says so; the gate does not protect against it. The paid run settles this.
- With API-key access a stop answers `fundsReleased: false` while Nosana reports the deployment as stopping; the status worker confirms the release on a later tick. Nosana returns the unused part of a job's debit as a `job_refund` row about a minute after the stop (settled from the account's transactions; the paid run records it for a deployment of ours). A transaction row carries no deployment id, so what Nosana charged cannot be tied to a deployment except by time; per market and day it can, through `/credits/spending-history`. Nothing reconciles our `gpu_usage` against either.
- A deployment whose create call threw may exist on Nosana as a draft with no id in any row. Its name (`wheelsai-model-<deployment id>-r<run>`, `wheelsai-agent-<deployment id>`) leads back to the row. The operator view lists such a draft under `untrackedDrafts` once it is 15 minutes old; nothing archives it automatically.
- Two deploys at the same moment can both pass the platform's credit gate. Nosana is the authority: the one it cannot fund ends as `nosana_insufficient_funds` and its hold is refunded.
- OpenClaw (decision of this build): not converted to a deployment now. It moves when its image is built, in both access modes, and that change also fixes its stop call.
- The reconciliation of Nosana's own list against our rows is a report, not an action. `GET /api/platform/compute` lists deployments named `wheelsai-*` that Nosana reports as starting or running (and, separately, as drafts), older than 15 minutes, that no row and no orphan record holds. Nothing stops them: an operator has to, in Nosana's dashboard. Automatic stopping waits until the paid run has shown what the list returns, and needs a re-check of our rows immediately before each stop.
- That report exists only when somebody opens the operator view. No worker runs it, and nothing alerts on it.
- No alert fires when the credit balance falls below `NOSANA_CREDITS_WARN_USD` or below the floor. The operator view says "low" or "blocked" and the public status page says "New deployments paused"; a low runway is logged once per deployment per runway interval by the billing worker. Whether an existing alert channel fits was not looked at.
- The operator view is JSON only (`GET /api/platform/compute`, `x-admin-key`). There is no page for it.
- The below-cost check refuses a deployment in the request path only with API-key access (there it also refuses when the cost is unknown, see above). With a wallet a tier priced below its Nosana cost is flagged in the operator view and logged when the view is read; nothing checks it on a timer or at boot.
- The public status component reads "operational" with wallet access whenever a wallet is loaded: it does not look at the wallet's NOS or SOL balance. With an API key it follows the balance, up to `NOSANA_CREDITS_CACHE_MS` plus the status page's own 10 seconds late.
- The operator view lists a wallet account's deployments through the SDK's wallet-signed list call. That path has only run against test doubles, and it throws for the whole list if one deployment's `owner` is not a public key (the API-key path reads the list directly and does not).
- A deployment whose `owner` is not a base58 public key can be found by name but cannot be read, stopped or scaled through the SDK (`nosana_read_failed`). On the founder's API-key account `owner` and `vault` are the same 44-character base58 key, so this does not arise there (settled 2026-10-07); it stays a property of the SDK until the port is replaced.
- The SDK drops the body of a 401, so when an API-key call fails the client asks the credit balance once to learn whether the key was rejected, and remembers the answer for `NOSANA_CREDITS_CACHE_MS`. That is one extra GET per failed call when the cache is 0.
- Every create sends an `idempotency_key` (the per-run name; a duplicate answers 409), and a create that threw is looked up by it. Nosana releases a key only when the deployment is deleted, so a Nosana name is never reused.
- An agent cannot be deployed on a model deployment: `POST /api/agents/:id/deploy` with `modelDeploymentId` answers `501` (`agent_model_deployment_unavailable`) before anything is reserved. The only address of a model deployment a Nosana node can reach is this API's `/v1/<slug>`, which needs an organization API key, and nothing delivers one to the agent's container. Open decision: a key that can call one model deployment and nothing else (today's scopes cannot express that; a key with no scopes has the organization's ordinary access), how it reaches the container, and its revocation when the agent stops. The API reference page, the SDK and the CLI still offer `modelDeploymentId`. The agent's own secrets are not placed in the definition either, so an agent on an external model that needs a key has none.
- An Ollama deployment turns `online` only after the model is pulled, but the model is loaded into the GPU by the first request, which is therefore slow. Nothing warms it.
- A deployment whose start call failed and that still reads DRAFT is kept by the reclaim sweep for 10 minutes (`DRAFT_START_HOLD_MS`), then released. A restart of that row answers `previous_run_winding_down` during those minutes. The window rests on the 300 s cap of `NOSANA_SDK_TIMEOUT_MS` and the runtime's own wait for response headers; a start that Nosana carried out later than that would not be seen.
- Training jobs are never observed on Nosana: the status worker reads model and agent rows only, so a training job that hits its timeout, an error or insufficient funds keeps its status until its own container reports or the user cancels. Left to the fine-tuning build, which also adds the deploy preflight to the training route.
- The dashboard's new-deployment page disables Deploy after a "paused" refusal until the user presses "Try again"; it does not re-check on its own. The dashboard has no replica control, so the scale-up refusal (`503` on `PATCH`) is reachable through the API only.
- A partial billing window at a replica change or a stop is charged a whole cent. Seen in the loopback run and left as it is.
- Still to be learned from the paid run: part 3 of `docs/NOSANA-DEPLOY-RUN.md` is the list. The ones a later change depends on:
  - whether create, start, stop and the replica update behave through the `/api` prefix on the dashboard host as the GETs do;
  - the time from Nosana's RUNNING to an endpoint with `online: true`, and whether the tunnel registers before the health check passes (if it does, `online` alone does not mean "serving");
  - a SIMPLE-EXTEND extension paid with credits on a deployment of ours, and whether `reservedCredits` ever moves;
  - the refund when a SIMPLE job completes on its own, and the minimum charge for a very short job (about $0.01 observed);
  - whether an INSUFFICIENT_FUNDS deployment resumes after a top-up in production as the manager's defaults say;
  - whether the on-chain market `jobPrice` is the host reward or the fee-inclusive price (wallet path), and whether the devnet hosts accept dashboard keys or hold credits;
  - an end-to-end pull from a private registry with `authentication.docker`.

## Custom domains

- **No certificate has been issued through the edge (major, blocks the claim).** The edge app, its addresses and its secrets do not exist yet (`docs/FOUNDER-ACTIONS.md` section 12). Everything up to the certificate authority was run locally (`docs/CUSTOM-DOMAIN-RUN.md`); the staging run listed there is what proves the claim.
- The dashboard pages for custom domains were type-checked and their wording unit-tested, but not opened in a browser against a running API.
- The host routing table holds every verified domain in each API machine's memory and reloads all of them every `CUSTOM_DOMAIN_ROUTE_REFRESH_MS`. A switch-off, new token or delete applies at once only on the machine that handled it; the others follow within one reload.
- The edge is one machine with one volume. A second machine needs shared certificate storage (a Caddy storage module), which is not built.
- The proof the checker asks for (`GET /.well-known/wheelsai-domain` through the edge) is a per-domain constant, answered for any verified domain including a paused one, and readable by anyone who can reach the hostname.
- An edge that asked about a hostname before it was verified is told "unknown" for up to 60 seconds after verification (the remembered answer), so the first certificate can be delayed by that long.
- The certificate question answers for a hostname only by its verified claim. Nothing limits how many unknown names one client can make the edge ask about, beyond the 60-second memory of "unknown".
- When the certificate question refuses a hostname because an issuance budget is spent (429 `issuance_budget_*`), the owner is not told why: the checker's handshake is refused by the edge and the domain reads as waiting for its certificate. The refusal is logged on the API only.
- The issuance budget counts every "yes" for a hostname without an observed certificate, including the repeats several simultaneous first handshakes cause, so a busy new hostname can use up to 5 of its organization's 30 for one certificate. It errs towards refusing.
- The per-organization domain limit and the issuance limits are server-wide settings (`CUSTOM_DOMAIN_MAX_PER_ORG`, `CUSTOM_DOMAIN_ISSUANCE_*`); there is no per-organization override for a customer who needs more.
- "Check now" (`POST /api/domains/:id/verify`) is limited only by the API's general rate limit; each call makes DNS lookups.
- Request counters count only forwarded requests made with the owning organization's credentials, and stop counting new domains beyond 10,000 buffered between flushes.
- Deleting a domain is two statements (the row, then its events), not a transaction; the worst case is orphan event rows.
- `API_HOST = "::"` (needed by the edge) also makes the API reachable by every app on the Fly organization's private network, with `X-Forwarded-For` trusted for one hop. Only the platform's own apps are on that network today.
- The PROXY protocol allow-list of the edge (`EDGE_PROXY_PROTOCOL_ALLOW`, default `172.16.0.0/12`) is the documented guess at where Fly's proxy connects from; it is confirmed or corrected on the first staging deploy.
- The deployments API reference page does not list `customEndpoint` yet; the custom-domains guide does.
- A member of an organization who owns no organization could not sign in during the proof run (`priya@northwind.ai`: "User has no organization"), so the owner-or-admin guard on domain writes was exercised by unit test only. The sign-in problem is outside custom domains and was not investigated.

## Measured latency

- Time to first token is recorded for streamed model-deployment answers only. An agent chat's sample comes from the usage hook (`services/agentUsage.ts`), which is told the chat's total time and nothing about its first token; `services/agentChat.ts` would have to pass it.
- Channel replies (Telegram, Discord, Slack) leave no latency sample. The agent-message worker calls the agent's node over HTTP outside the shared agent-chat core, and its binding carries neither the organization nor the agent id a sample needs.
- A request that fails with an unhandled exception after the inference node answered (a settle that throws, for example) is answered 500 and leaves no sample on `/v1`; the workflow path (`runDeploymentChat`) samples it as an error.
- The sink holds up to one second of samples in memory (5,000 at most) and drops, with a count, what it cannot write. A process that is killed without closing loses that second. A statement that fails is halved until the unwritable row is alone (at most 200 further statements per batch of 1,000; the search stops after about 14 when nothing at all can be written), so a batch with very many unwritable rows can still lose writable ones. `droppedFailed` and `droppedOverflow` are logged and not exported as a metric.
- The public figure counts each organization's most recent `ceil(PUBLIC_LATENCY_MIN_SAMPLES / PUBLIC_LATENCY_MIN_ORGS)` requests (17 at the defaults) and no more. That bounds one organization's share; it does not make organizations expensive. One person who signs up enough free organizations, and sends real chats from each, can still reach the thresholds and supply every sample. Closing that needs a rule on which organizations count (a verified email, an age, a paid plan, or an allow-list) that the founder has not chosen.
- With the cap, one organization can hold up to about a third of a just-published figure's samples (17 of 50). That cannot set the p50, and it can set the p95: a p95 is the slowest twentieth, so any organization with more than 5% of the samples can raise it. The share shrinks as more organizations send traffic; a p95 that no single organization can move needs more than 20 organizations at the cap, or a lower cap.
- The cap is derived, not configurable, so it cannot be set apart from the thresholds. An operator who wants a different share changes the two thresholds.
- The error share on `/status` is capped the same way but over every ending, while the latency figure ranks answers only; the two rest on overlapping, not identical, rows of an organization.
- An agent chat's time is measured from the start of `prepareAgentChat`, so the HTTP guard and body parsing before it are not in an agent sample; a model deployment's sample on `/v1` includes them.
- `agent_usage_records.latency_histogram` and `total_latency_ms` are still written and no latency is read from them any more: every average and percentile comes from `request_latency_samples`. The histogram's sum is still what `answered` is counted from (`summarizeAgentUsage`), so dropping the two columns needs an `answered_count` column first.
- Samples past `LATENCY_SAMPLE_RETENTION_DAYS` are deleted by the analytics-snapshot worker. With `ANALYTICS_SNAPSHOT_INTERVAL_MS=0` nothing prunes; a prune of its own, independent of that worker, is not built.
- An analytics period longer than the retention (or reaching back before samples existed) states the latency of the days that still have samples, without saying the period is only partly covered. Daily snapshots keep each day's figures beyond retention; the overview does not read them.
- Legacy analytics snapshots keep `avg_latency_ms` as it was: a true mean, of node time on model deployments only. Newer rows hold the mean end-to-end time of answered requests, so a history chart crossing the release mixes the two.
- The public figure is cached per API instance (60 s, stale for at most 10 minutes on a failed read). Two instances can state figures computed up to a minute apart; each carries its `computedAt`.
- The `insufficient_data` state gives the sample count and both thresholds but not the number of organizations, so "enough requests from too few organizations" reads as "measuring" with a count already above the minimum.
- `latency_p95` and `latency_avg` rules stored before the evaluator computed them carry thresholds entered with no unit; they are now read as milliseconds (see `docs/FOUNDER-ACTIONS.md`). Nothing migrates or pauses them.
- Alert rules are validated in `services/monitoring.ts` (`alertRuleProblem`), and the routes answer its message as a 400; the route bodies themselves are still untyped casts, and an alert rule row records nothing about its last evaluation (value, no data, failed), so the dashboard cannot show why a rule is quiet.
- The CLI ships compiled and depends only on the SDK, so it carries its own copy of the latency line formatter (`packages/cli/src/lib/latency.ts`, copied from `packages/shared/src/latency.ts`). `apps/api/src/tests/latencyLine.unit.test.ts` fails when the two differ; one shared, built package would remove the copy.
- The shared formatter is imported as `@wheelsai/shared/latency`, a subpath export. It is not re-exported from the package index, because the index is consumed by both NodeNext (`.js` specifiers) and the web bundler.
- `wheelsai deploy` prints the platform's figure, not the deployed agent's own. An agent's own p50 exists (`GET /api/agents/:id/usage`) once it has answered requests; the command does not switch to it.
- The landing page reads the figure from the browser, so a build without `NEXT_PUBLIC_API_URL`, or an API whose `CORS_ORIGIN` leaves the site out, always shows "live figure unavailable" (see `docs/FOUNDER-ACTIONS.md`).
- The landing latency cases in `apps/web/e2e/landing.spec.ts` have not been run: the installed Playwright browser build does not match the project's Playwright version. The page was rendered with the installed Chromium for `docs/LATENCY-RUN.md` instead.
- `GET /api/analytics/overview` counts `totalRequests` from model-deployment usage records only, while its latency fields cover agent chats too: an organization with only agent chats reads "0 requests" next to a measured latency (seen in `docs/LATENCY-RUN.md`).
- `packages/sdk/dist` predates the `latency` fields on `PublicStats` and `PlatformStatus`; the CLI reads the block untyped, so it does not depend on a rebuild, but SDK consumers need one.
- The terminal preview's field lines lose their column alignment in the browser (runs of spaces collapse); the lines are not rendered `whitespace-pre`.

## Web chat channel and Try it

- **Try it cannot preview an agent whose entrypoint is its graph (major, narrows the "every listing" claim).** A graph's nodes choose their own models and provider keys, so the run cannot be moved onto the platform's free models, and running it as it is would spend the publisher's keys for anonymous visitors. `runPublicChat` answers 501 `not_supported` / `graph_agent_preview` for such a listing, and `prepareAgentChat` refuses a platform-funded graph chat as a second guard. Closing it needs a model override that reaches every llm node of a graph run (`services/runAgentGraph.ts`).
- The limiter counts attempts, not answers: a message that is admitted and then fails at the model still uses one of the key's daily cap, or one of a listing's platform-funded messages for the day. A publisher-funded message is the exception (it is refunded, and its count with it).
- A wildcard origin is refused directly under a top-level name (`https://*.com`) but there is no public-suffix list, so `https://*.co.uk` is accepted.
- A widget message is counted against its key's limits and the owner's plan before the organization's free-model allowance (so a key's cap bounds what visitors can spend of that allowance). The other side of that order: while the allowance itself is used up, each refused widget message still uses one of the key's daily cap and one of the plan's API calls, at most the key's cap a day. Closing it needs a limiter that counts the key and the organization in one step.
- The widget has no per-session limit. Its session id is chosen by the client, so a limit on it would bound nothing; the per-address and per-key limits are what hold.
- All limiter keys share one Redis hash tag so the multi-key script runs in Redis Cluster, which also puts every public-chat counter in one slot.
- The limit of 20 live keys per agent is a count followed by an insert, not one statement: two creations at the same moment can leave an agent with 21. It bounds a list and guards nothing.
- A publisher-funded Try it message that finishes later than 15 minutes after its hold is refunded by the reaper even if its answer then arrives (the late settle changes nothing). Chats are cut off long before that (`AGENT_CHAT_TIMEOUT_MS`, at most 10 minutes), so the gap is only reachable by raising that limit past the reaper's.
- Publisher-funded message revenue is taken from the publisher's credits and recorded as `trial_usage` ledger rows and `trial_charges`; it is not yet in a platform revenue report.
- Limiter refusals (`rate_limiter_unavailable`) are logged at error level but raise no alert of their own; while Redis is down every widget and every Try it answers 503 by design.
- The widget's configuration and chat routes are also behind the API's global per-address limit (100 a minute, fails open). A site whose visitors share one address (an office, a carrier NAT) reaches the widget's own per-address limits first.
- A server started with no Redis at all answers no request on any route (seen in the proof run, `docs/WEB-WIDGET-RUN.md` section E4: nothing came back within 20 seconds). The public chat limiter itself reported "did not connect" and would have refused; the request never reached it. When Redis goes away under a running server the public routes answer 503 in milliseconds, as designed. What hangs a cold start is the API's other Redis-backed plumbing (the global rate limit and the queues), which is outside this feature.
- OpenClaw channel rows saved as `web` before the "Web Chat" option started creating a web chat key are still in the table. Nothing serves them and the public agent page shows them as "configured, not live yet"; they are not converted into keys.
- `apps/web/public/widget.js` is served with `Cache-Control: public, max-age=300` and no version in its address, so a fix reaches every embed within five minutes and a breaking change to the widget routes has to stay compatible with the script of five minutes ago.
- The widget was run in headless Chromium only (`e2e/widget.spec.ts` and the proof run). Firefox, Safari, a phone and a real screen reader have not been tried.
- The repository's `@playwright/test` and `playwright-core` want different Chromium builds; the two new specs were run with the installed one through a throwaway config. `npm run test:e2e` as configured needs `npx playwright install` first.
- The model catalog labels `free/groq/llama-3.3-70b` "GPT-OSS 120B (Groq)", and the Try it tab shows that label as the answering model. The label is the catalog's (it predates this work); whichever is true, the id and the label should name the same model.

## Fine-tuning

The training container (`infra/training/`). Its README ends with what stays unproven until a GPU run; these are the known gaps in what was built.

- **The image has never been built (major until done).** The Dockerfile passes `docker build --check`, its base digest was read from the registry and its pins resolve together, but the multi-gigabyte base was not pulled, so no layer has run. The `trainer-image` CI job has never run either.
- **Nothing of the GPU path has executed**: QLoRA 4-bit loading, bf16 autocast, gradient checkpointing, the VRAM fields of `metrics.json`. On CPU `METHOD=qlora` is refused with exit 10 and that refusal is the only QLoRA behaviour under test.
- None of the catalog's base models (Phi-3, Qwen2, Llama 3.x, Mistral) has been loaded by the trainer. The CPU proof used SmolLM2-135M; chat-template handling is tested against three synthetic templates (ChatML, strict alternating with no system role, one that drops the system role), not the real ones.
- `"all-linear"` is resolved by peft per architecture. On Llama-shaped models it gives the seven attention and MLP projections (tested). Whether vLLM accepts every module it yields on Phi-3 (`qkv_proj`, `gate_up_proj`) is unknown; the plan is to restrict `targetModules` per base model after the first serve test.
- Exit 13 (out of memory) is recognised by exception type and message and is tested by raising the error by hand. A host that kills the process for memory (SIGKILL) leaves exit 137 and no `failed` event; the API ends such a job as failed, charged nothing, so the user is not told it was memory.
- A run is not resumable on a node. Checkpoints are written per epoch to local disk and `--resume-from` works (tested), but nothing uploads a checkpoint, and dropout's random stream is not restored on resume.
- When `MAX_RUNTIME_SECONDS` is reached before the first optimiser step (a slow model download, say), the trainer keeps going until the host stops it and exits 30. The API charges nothing for any interruption the user did not ask for, at the run limit or not (it was charged as `run_limit_reached` before the review: Nosana's timeout after a slow image pull looked the same, and the pull is the platform's). Such a run ends `failed`, `interrupted`, free, and counts toward the organization's free failures. The trainer's own stop at its limit (exit 0, partial adapter) is still a charged completion.
- Callback delivery is best effort by design: an event that fails three tries is skipped and later ones still go out, so the receiver sees gaps in `seq`. The complete record is the stdout log. The API reads it from the finished job's result (proven against the stand-in only); whether Nosana returns a finished confidential job's logs is unverified.
- A dataset is tokenised in memory. At the planned limits (200 MB, 200,000 rows) that is a few hundred megabytes of Python lists; nothing in the trainer enforces those limits itself, it trains on whatever the URL returns.
- `sharegpt` rows accept only the roles `human`, `gpt` and `system`, as the API's validation does. Datasets using `user` / `assistant` are refused at validation and by the trainer.
- Transitive Python dependencies are pinned in `requirements.txt` to the versions the CPU suite ran with; packages that only torch needs are left to the base image and are not pinned.
- The trainer's lint (`ruff`, settings in `infra/training/ruff.toml`) is not a CI job; only the pytest suite is.

- A SIGTERM that arrives while the trainer is draining its last callbacks (`sender.close` in `runner.main`) is not caught, so the process can end with another code after it already printed `completed` or `failed`. This happens on every run that reports by callback, because the API stops the deployment as soon as the final event is in (seen in the local proof: the process ended by SIGTERM after `completed`). The API takes the final event over the exit code, so the job's outcome is right; the trainer's own exit code is not.
- The offline trainer tests assert that the adapter weights moved and the logits changed, not that the loss fell. Only `scripts/cpu_proof.py`, which is not a CI job, shows the fall.
- The trainer redacts the query string of its four URLs. A local-driver transfer URL carries its token in the path; no message prints a URL today, so nothing leaks, but the redaction would not cover it.

Object storage and datasets (`apps/api/src/services/objectStore.ts`, `dataset.ts`; run log in `docs/OBJECT-STORAGE-RUN.md`):

- **No real bucket has been used.** The S3 driver is proven against MinIO only. On Cloudflare R2 two things are unconfirmed: that a presigned PUT signed for `content-length` is enforced, and the bucket CORS rule for the browser upload. `apps/api/scripts/object-store-smoke.ts` settles the first; one upload from the deployed dashboard settles the second.
- A presigned PUT can carry a size limit only when the exact size is known up front. Dataset uploads have it (the browser declares the file size). An adapter uploaded by the training container does not, so its size is checked from storage when the job is finalised (limit `TRAINING_ADAPTER_MAX_BYTES`), after the bytes are already in the bucket: an oversized or unwanted upload is refused then, not prevented, and its object is not deleted.
- Validation runs inside the HTTP request. It took about half a second for 149 MB from local disk; from a remote bucket it is as slow as the download, and a 200 MB file may outlast a proxy timeout. If it does, it becomes a queued job with a `validating` state.
- Parquet: the magic bytes are checked and the row count is read from the footer's own metadata (`num_rows`), so the row limit applies. The count is what the file declares; the rows are not read, a file whose footer lies trains on whatever it really holds, and there are no token figures for Parquet. A Parquet job is therefore bounded by its run limit only: there is no estimate for it, so `POST /estimate` with a run limit answers `estimate: null` with the `hold`, without one `422 training_estimate_unavailable` asking for it, and `POST /jobs` without one answers `400 run_limit_required`. The new-job page requires the run limit for such a dataset and reviews the hold without an estimate. A footer that cannot be read (or is longer than 8 MiB before `num_rows`) leaves the count unknown (`rowCount` is `null` in the API, `row_count_known = false` in the table): such a dataset validates but `POST /jobs` and `POST /estimate` refuse it with `422 dataset_row_count_unknown`. Reading the row groups to count for real is not built.
- **The upload link outlives validation.** A dataset's presigned PUT (or local token) works for an hour and any number of times, so the object can be replaced after it was validated, or re-created after the dataset was deleted (an orphan nothing sweeps). Validation now stores the sha256 of the bytes it read (`Dataset.contentSha256`) and the store's ETag (`contentEtag`). The job service passes `contentSha256` to the trainer as `DATASET_SHA256` and refuses a job with `409 dataset_changed_since_validation` when `datasetObjectState` says the object is not the one validated, at create and again at submit. A swap made after the submit and before the download still costs a failed run (exit 11, `dataset_checksum_mismatch`), and that run is charged to the organization for the seconds it ran. Links cannot be revoked; a shorter lifetime, or a bucket policy that forbids overwriting, would narrow the window.
- A NUL character or an unpaired surrogate in a row is a validation error in the API (Postgres cannot store either in `jsonb`). The trainer has no such rule: it would accept a NUL, and an unpaired surrogate most likely fails inside the tokenizer. This only matters for Parquet, whose rows the API does not read.
- Sample rows are a cut-down preview (strings to 400 characters, 20 keys or items per level, at most 64 KiB per dataset) and error messages are cut to 300 characters. The detail endpoint still loads both JSON columns; the list does not.
- The API's row validation (TypeScript) and the trainer's parser (Python) are two implementations of the same four formats. Nothing pins them to each other; a shared set of fixture files run by both suites would.
- Token figures (`avgTokensPerRow`, `totalTokens`) are characters divided by four over every valid row, not a tokenizer's count.
- One bad row makes a dataset invalid. There is no option to drop bad rows and train on the rest.
- A failed object delete is logged with the object's URL and nothing else: no sweep collects it. The same is true of a dataset that was created and never uploaded (the row stays "pending"), and of an upload that was never validated.
- When validation rejects a file for being over a limit it deletes the object but keeps the row with the reason. There is no way to upload again into the same dataset; the user deletes it and starts over.
- No per-organization storage quota or dataset count limit exists, only the per-file limits. Since the review fixes a dataset row is small whatever was uploaded (the list no longer reads the JSON columns), so the count is a storage-cost question, not a memory one.
- Rows created before this change that point at another bucket (`s3://other-bucket/...`), including the seeded demo dataset, cannot be validated: they answer `409 dataset_not_uploaded`.
- The local driver is for development: its transfer tokens can be used more than once until they expire and sit in the URL path (so in request logs), and per-agent files stay unavailable with it (they need the S3 client).
- CSV: comma-delimited only, header names matched exactly (`prompt`, `completion`, `text`), values trimmed. A single row is limited to 4 MiB in every file type.
- The datasets page counts rows before upload for JSON Lines only (CSV and Parquet are counted, or not, by the server), and was not opened in a browser in the proof run. Its older colour classes (`text-red-500`, `bg-blue-500/10`) predate this change and are not semantic tokens.

The job service, the poller and billing (`apps/api/src/services/trainingJobs.ts`, `trainingBilling.ts`, `trainingStateMachine.ts`, `queues/training-poller.queue.ts`; run log in `docs/FINE-TUNE-RUN.md`):

- **No training job has run on Nosana or on a GPU (major until done).** The whole pipeline ran on one machine against a stand-in Nosana API whose node started the trainer as a CPU process with a 135M-parameter model in place of the catalog model. Part 3 of the run document lists what that leaves unverified; the items below are the ones with a consequence in code.
- Everything the poller reads from Nosana is read by shapes taken from the SDK's types: that a finished job's result carries `opStates[].exitCode` and `logs`, that a confidential job's result is readable at all, that a `SIMPLE` deployment lists exactly one job (the first listed is followed), and that `timeStart` and `timeEnd` are unix seconds. If the result is not readable and the callbacks never arrived, a finished run ends `failed`, `no_exit_code`, charged nothing, 300 seconds after its end was seen, although its adapter may be in storage.
- Billing starts at the Nosana job's `timeStart` when it is plausible, otherwise at the trainer's first callback. If Nosana's start is before the image pull, the pull is billed to the user (the hold still caps the charge, and the trainer's own limit counts from its process start, so the run is not cut short). Unknown until a run.
- Most ended jobs leave a record for the orphan sweep (5 of 8 in the local proof): Nosana answers a stop with "stopping", so the release cannot be confirmed in the same call, and the job is settled once the record is written. The sweep is part of the deployment status worker. Job creation now refuses with `503 training_orphan_sweep_disabled` when `DEPLOYMENT_STATUS_INTERVAL_MS` is 0 (also a capabilities blocker). It reads the setting of the API process that admits the job: a deployment that runs the workers in a separate process with different settings is not checked.
- A cancel is settled as soon as the stop is requested and recorded, not when the GPU has stopped. The organization is charged to the request; the platform pays Nosana for whatever the stop then takes, and for a stop that fails until the sweep succeeds.
- The API stops the deployment as soon as the trainer's `completed` or `failed` event is in and, for `completed`, the adapter is verified. That is by design (it saves GPU time), and it means the process is ended by SIGTERM during its own shutdown on every run that reports by callback.
- A submit whose create call failed and whose name lookup keeps failing is refunded after one hour anyway, with an error log naming the deployment. If the deployment exists it runs to its Nosana timeout at the platform's cost.
- The per-organization limit on unfinished jobs and the free-failure limit are checked inside the create transaction after its first statement, an update of the organization's `credit_balances` row that adds 0 and so takes that row's lock: concurrent creates of one organization take turns and each counts the others' committed jobs. Checked on a Postgres copy: six concurrent creates with a limit of 2 admitted 2 (all six without the lock). An organization with no `credit_balances` row is refused `402`.
- **Free failures are bounded per organization**: at most `TRAINING_FREE_FAILURES_PER_DAY` (default 3) jobs may end failed and charged nothing in a rolling 24 hours (a job cancelled after its run had already failed free counts too; rows from before billing do not). At the limit create and retry answer `409 training_free_failure_limit` with `retryAt`, and capabilities list the same sentence. Every free failure counts, including the ones that cost the platform no GPU time (`submit_failed`, `no_capacity`) and the ones a platform fault causes for everyone (an image that cannot be pulled): an outage can lock organizations out for a day. Narrowing it to the codes a user can steer (memory, base model, `killed`) is a product decision.
- A cancel cannot change what had already happened. Once the trainer's terminal event is recorded, cancel answers `409 training_already_finished`. A cancel of a run that turns out to have ended before the request is settled as it ended: completed first goes `cancelling -> finalizing` and is charged as a completion (never past the request); failed first ends `cancelled` with the failure's code, charged as that failure is. "Before" is certain when the end was recorded while the job was running (`gpuStoppedAt`); on Nosana's or the trainer's clock alone, an interruption, 143 or 137 is taken as our own stop. With the end seen but no exit code yet, the cancel waits the same 300 s for the result as a running job.
- The poller takes jobs least recently examined first (`training_jobs.last_reconciled_at`, null first) and stamps them as it takes them, so with more than 200 unfinished jobs each is still reached within ceil(n / 200) ticks.
- Each reconcile reads the whole job row, including up to 1 MiB of stored log text, for every unfinished job on every tick.
- A charge is rounded up to a whole cent per job, so a run that fails for a data reason after three seconds costs one cent. A hold is rounded up the same way.
- A tier that is in the price table but has no market on the configured network answers `400 unknown_gpu_tier`, not `501 gpu_market_not_configured`. With no Nosana credential at all the answer is `501 nosana_not_configured` (fixed in this build; it was the same 400).
- A callback over 64 KB is refused by the body parser, so the 413 body reads `FastifyError`, not `callback_too_large`.
- The callback secret and the adapter download signature are derived from `JWT_SECRET`. Rotating it while a job runs leaves that job to be finished from the Nosana logs alone.
- The estimate is planning arithmetic: fixed 240 s image pull, 185 s set-up, 60 s wrap-up, and a throughput formula from the parameter count. At the minimum run limit (300 s) it reports that even a 40-row job may not fit. Nothing has been measured on a GPU; the catalog's memory figures per model and method are of the same kind, as is which models are gated.
- A platform-caused failure is not retried. The user starts the job again (`POST /jobs/:id/retry`), which takes a new hold.
- Organization webhooks (`training.started`, `.completed`, `.failed`, `.cancelled`) are unit tested; the local proof did not register a webhook and observe a delivery.
- Training usage is counted in the monthly spend projection (`services/analytics.ts`). Other spend views, in the API or the web app, were not checked for it.
- A job row created before this build (no hold) that is not finished is ended as failed and charged nothing by the poller; it is never submitted.
- The README says fine-tuned models are served per request via x402. What is built serves a fine-tuned model from a dedicated deployment billed per GPU-second to its owner, with requests included; no per-request x402 price exists for one. The line was left unchanged (see `docs/FOUNDER-ACTIONS.md`, section 16).
- `apps/api/scripts/run-fine-tune-local-proof.ts` needs the seeded demo owner, the trainer's Python environment and the cached small model on the machine, and is not a CI job.

Serving a fine-tuned adapter (`apps/api/src/services/fineTunedModels.ts`, `routes/fineTunedModels.ts`, the adapter definition in `services/nosana.ts`):

- **No adapter has been served on a GPU.** Unproven until a paid run: that a Nosana node honours `entrypoint: ["python3", "-c"]` with an array `cmd`, that vLLM 0.6.0 / 0.6.3 loads the trainer's archive with `--lora-modules` (it refuses target modules it does not support), and that the node can reach `PUBLIC_API_URL`.
- The tier check for serving (`servingVramGbForParams`: 2 GB per billion parameters plus 1) is a planning figure. It refuses an 8B base on a 12 GB tier, which an ordinary deployment of the same base is still allowed to pick; the ordinary path has no tier check at all. A 70B fine-tune fits no single-GPU tier unquantised, so it can be trained and not served.
- The adapter URL never expires by design and is revoked by the deployment row (stopped, restarted or deleted model). Its signature sits in the query string, so it appears in this API's request log and in any proxy log in front of it. It is signed with `JWT_SECRET` under its own domain string: rotating that secret breaks the URL inside every running adapter deployment, which then cannot re-fetch after a re-list until it is restarted.
- A deployment that is re-listed on a new host fetches the adapter again. If the fine-tuned model's objects are gone (storage loss) the container exits 78 and the deployment fails; nothing reports that reason to the dashboard beyond the status.
- Deleting a fine-tuned model marks the row deleted and then removes its objects. A failed object delete is logged and not retried; no sweep collects it. The metrics file is removed only when it sits beside the archive in a directory named for the training job.
- A deployment serves one adapter. Several adapters on one base model (vLLM supports it) is not built.
- `--max-lora-rank` is the smallest value vLLM 0.6.x accepts (8, 16, 32, 64, 128, 256) that is at least the adapter's rank (`vllmMaxLoraRank`), so a rank-4 adapter is served under 8; vLLM refuses `--max-lora-rank 4` at startup. Read from vLLM's `LoRAConfig`, not observed on a node.
- `wheelsai/ft-<slug>` resolves for agents (`services/hostedModel.ts`), and `wheelsai/<base id>` no longer resolves to a deployment that serves an adapter. No page offers the `ft-` form yet.
- The served-model check of a workflow model step accepts the base model's id for a deployment of a fine-tune of it.
